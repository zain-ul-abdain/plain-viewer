## Safety scope

Markdown image/file references are never followed by implemented code. Links require an allowed scheme and confirmation; the confirmation shows, and Windows receives, the percent-encoded address (LinkPolicy.LaunchAddress), so quotes and spaces in a document's link cannot add arguments to the browser or mail program. Document HTML/XAML is never instantiated. The worker uses a Windows Job Object with a 256 MB memory cap, one-process limit and kill-on-close. Parent enforces 20 seconds for opening and 32 MB for serialized output.

Privilege isolation (Zain's gate 1 decision, DECISIONS.md): the worker drops to low integrity before it reads a document and refuses to continue if it cannot; LibreOffice is started at low integrity in a Job Object limited to its launcher plus one process. At low integrity Windows stops them writing the user's files and registry and opening other programs to change them (tested: `test.ps1` low-integrity test; all LibreOffice processes observed at low integrity). They can still read files the user can read. PDF pages (PDF.js) and the spreadsheet grid run inside WebView2, in Chromium's renderer sandbox.

Network: the installer's optional "firewall" task adds Windows Firewall rules, after one administrator prompt, that block the worker, LibreOffice and LibreOffice's Python in both directions; About shows whether they are present. Without those rules there is no OS-level network block for the worker or LibreOffice, only the layered measures (sanitised copies, hardened LibreOffice settings, dead proxy). Even with them, network access that Windows performs for a program through system services (DNS lookups, network-share access by the SMB client) is not covered. This is weaker than an AppContainer, which LibreOffice cannot run in. Worker failures are tested (scripts/test-worker.ps1, through the app's own WorkerClient): a crash or half an answer gives a plain message ("The document worker stopped unexpectedly…"), a hang is stopped at the time limit, Cancel stops the worker within a second, the 256 MB limit stops a worker that keeps allocating (it stopped at 176 MB), the worker cannot start another program, output past 32 MB is refused, no worker process is left behind, and the next file opens normally. The original is opened by Core/LocalFiles.cs after the path check: a link in the last part of the path is opened as a link (not followed) and refused, a cloud placeholder is not downloaded by opening it, and the opened file itself must be an ordinary, available file on a local drive (its own final path is checked, so a folder swapped for a link to a network share between the check and the open is refused before anything is read). Change checks use the open file, so a file replaced at the same path during opening does not mix two files. Limit: Windows follows a link in a folder of the path while opening, so a link created in that moment may already have been followed when it is refused; creating such links needs administrator rights or Developer Mode.

Originals use shared read/write/delete access. Current text paths keep data in memory and make no temporary disk copies. Final modification checks may reject a source moved during opening. Signature/control-character screening rejects obvious binary mismatches; extension selects presentation among text/CSV/Markdown, which have no unique magic bytes.
